Quickstart

Create an API key in the authenticated Dashboard. The full key is shown once. Store it server-side and send it as a Bearer token.

export ELOFID_API_KEY="YOUR_API_KEY"
export ELOFID_API_BASE="https://api.elofid.com"

curl "$ELOFID_API_BASE/v1/watchlists" \
  -H "Authorization: Bearer $ELOFID_API_KEY"
Use the API key shown once in the Dashboard. Treat the key value as opaque, keep it server-side, and never commit it to source control.

Authentication

Customer API routes use Authorization: Bearer <API_KEY>. API keys are generated server-side, stored as hashes, and the plaintext value is only returned on create or rotate.

Lost a key?

Rotate in the Dashboard, update your application, then revoke the old key. Saved keys are masked and cannot be revealed again.

Keep keys server-side

Do not ship Elofid API keys in browser bundles, mobile apps, public repositories, or client-side logs.

Free plan behavior

Free includes full Events and Risk Incidents for the assets the workspace monitors, bounded by the 7-day My Monitoring history window. Global Intelligence is a real, sanitized preview only. Full Global Feed API access requires Starter or higher.

Removing an asset is a soft pause: history is preserved. A replacement is consumed only when a unique workspace chain+token monitoring slot is actually released. Re-adding the same paused row reactivates it.

Global Intelligence / Global Feed

Global Intelligence is network-wide intelligence detected by Elofid across monitored assets. Free workspaces receive a bounded real preview in the Dashboard. Customer API-key access to the full global routes requires global_feed_access=full (Starter+).

Free API keys do not receive Full Global Feed. Paid-only global requests fail before API metering, so a denied Free request does not consume monthly API quota.

Webhook Destinations

A Webhook Destination is one configured endpoint. It is not a delivery/message quota. One destination may receive many Event and Incident deliveries. These destinations cover the monitored lifecycle delivery model. Global Webhooks are not currently a separate product. Destinations must be public HTTPS URLs. Registration blocks credentials, fragments, literal IPs and local/internal hostnames. Delivery-time validation also rejects private/reserved resolved addresses.

Each delivery has a type. Events are delivered as elofid.event.created, elofid.event.updated and elofid.event.resolved. Risk Incidents use the same three under elofid.incident.*. A test delivery is elofid.webhook.test.

GET/v1/webhooksmetered

List configured Webhook Destinations and operational state.

POST/v1/webhooksmetered

Register a Webhook Destination. Final limits are Free 1 · Starter 3 · Growth 10 · Pro 25 · Enterprise Custom, enforced server-side.

Soft-revoke the endpoint. Delivery audit history is preserved and the plan slot is released.

Verify webhook signatures

Elofid signs the exact raw request body with HMAC-SHA256. Do not parse and reserialize JSON before verification.

HeaderPurpose
Elofid-Signaturev1=<hex HMAC>
Elofid-TimestampUnix timestamp used in the signed message.
Elofid-Delivery-IdStable delivery identifier for deduplication.
Elofid-Webhook-IdElofid webhook ID.
Elofid-Signing-VersionSignature contract version.
Elofid-Secret-VersionSigning-secret version used for this delivery.
import crypto from 'node:crypto';

function verifyElofidWebhook({ rawBody, timestamp, signature, secret }) {
  const signed = `${timestamp}.${rawBody}`;
  const expected = 'v1=' + crypto.createHmac('sha256', secret)
    .update(signed)
    .digest('hex');

  const a = Buffer.from(expected);
  const b = Buffer.from(signature || '');
  return a.length === b.length && crypto.timingSafeEqual(a, b);
}

Delivery semantics

At least once

Consumers must be idempotent and deduplicate using Elofid-Delivery-Id.

Retries

Transport/DNS failures, 408, 409, 425, 429 and 5xx are retryable. Other 3xx/4xx outcomes are dead-lettered immediately.

Maximum attempts

Delivery processing allows up to 6 attempts before the row is dead-lettered.

Test is not production health

A successful /test proves connectivity/signing but does not pretend that a Production Event or Incident has been delivered.

Events vs Incidents

Event means one meaningful atomic change. Risk Incident is the correlated higher-level story and lifecycle built from related canonical Events. Several changes should become one coherent Incident when the correlation policy supports it, rather than a burst of unrelated alerts.

Event lifecycle

An Event is open while its condition holds and becomes resolved when it ends. A resolved Event may carry a resolution_reason.

resolution_reasonMeaning
monitoring_endedElofid stopped monitoring the asset. The Event also has monitoring_ended: true. It does not mean the risk went away.
semantic_version_changedElofid changed how this signal is measured. The open Event was closed instead of being compared across two different measurements.
slow_drain_recoveredThe slow drain signal fell below half of its opening threshold on two consecutive observations.
sell_restoredSelling works again.
buy_restoredBuying works again.
tax_normalizedThe tax returned to a normal level.
all_supporting_events_resolvedRisk Incidents only. Every Event that supported the Incident is resolved.
Treat resolution_reason as an open list. Handle values you do not recognise, and expect null on some resolved Events.

Errors & limits

API errors use a stable shape. Quota responses may also include a usage object and Retry-After.

{
  "ok": false,
  "error": "asset_replacement_limit_reached",
  "message": "Asset replacement limit reached.",
  "detail": "...",
  "usage": {
    "used": 5,
    "limit": 5,
    "remaining": 0
  }
}
Elofid fails closed where required evidence, entitlement configuration, destination safety, or exact intelligence support cannot be verified. Free requests for full Global Feed API access return global_feed_requires_paid_plan.

Exit Intelligence

Exit Depth is execution intelligence, not TVL and not gross pool liquidity. Where Exit Intelligence appears in Elofid data, unsupported or unverifiable coverage must remain explicit as null, partial, or unsupported rather than being invented or converted into token risk.

The current Developer API documentation does not invent a standalone Exit Depth endpoint that the deployed customer API does not expose. Endpoint-level Exit Intelligence documentation will be expanded only when that public contract is frozen.
